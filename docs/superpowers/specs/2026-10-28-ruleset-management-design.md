# YARA 룰셋 관리 설계

작성일: 2026-10-28
기준 브랜치: `develop` 61c9425

## 의도

관리자가 콘솔에서 YARA 룰을 관리하는 화면을 만든다. 관리자는 `.yar` 파일을 올려 새 룰셋 버전을 만들고,
원하는 버전을 활성화하고, 룰 하나하나를 켜고 끈다.

화면이 목표다. 다만 화면에서 바꾼 것은 탐지에 실제로 반영되어야 한다. 활성화하거나 룰을 끄고 켜면
탐지 엔진이 바뀐 룰로 검사하고, 이전 룰로 내린 판정은 다시 검사되어야 한다. 이 반영 과정은 데모에서
보여주지 않지만 반드시 동작해야 한다.

## 목표

- 룰셋 버전 목록, 버전별 룰 목록을 보여준다.
- `.yar` 파일 업로드로 새 버전을 만든다. 문법이 틀린 파일은 거부한다.
- 버전을 활성화한다. 활성 버전은 항상 정확히 하나다. 이전 버전을 다시 활성화해 되돌릴 수 있다.
- 룰마다 사용 여부를 켜고 끈다.
- 활성화와 룰 사용 변경은 탐지에 반영되고, 엔진이 내린 기존 판정은 재검사 대상이 된다.
- 업로드, 활성화, 룰 사용 변경은 감사 로그에 남는다.

## 범위 밖

- 브라우저에서 룰 원문을 보거나 고치는 기능
- 기존 버전에 파일을 추가하는 기능. 업로드는 항상 룰셋 전체를 교체하는 새 버전이다.
- 룰셋 삭제
- ADMIN/ANALYST/VIEWER 역할 구분. 다른 관리 API처럼 로그인만 확인한다 (`docs/auth-policy.md`).
- 파일 타입 정책 API (같은 스프린트 항목이지만 이번 범위 아님)
- 활성화 후 재검사되는 장면을 데모용으로 보여주는 기능

## 실패로 보는 것

- 업로드만 했는데 탐지에 쓰인다.
- 활성 버전이 0개거나 2개 이상이 된다.
- 콘솔은 v3가 적용 중이라고 보여주는데 엔진은 다른 룰로 검사한다 (엔진 재시작 뒤 포함).
- 룰을 껐는데 그 룰에 걸린 파일이 계속 차단된다.
- 활성화 뒤에도 이전 룰로 내린 엔진 판정이 캐시에서 그대로 쓰인다.
- 화이트리스트/블랙리스트 판정까지 stale 처리된다.
- api-server가 업로드된 룰 텍스트를 직접 해석한다 (프로젝트 원칙: 신뢰할 수 없는 입력의 해석은 엔진 쪽).

## 정해진 것

### 사용자가 정한 것

- 화면은 좌우 2단. 왼쪽은 버전 목록, 오른쪽은 고른 버전의 룰 목록과 "이 버전 활성화" 버튼.
  대기 중인 버전의 룰도 활성화 전에 볼 수 있다.
- 제목, 필터, 표, 버튼 같은 기본 레이아웃은 화이트리스트 화면(`console/src/pages/WhitelistPage.tsx`)을 따른다.
- 업로드는 기존 룰을 통째로 교체하는 새 버전을 만든다. 업로드 직후에는 비활성("대기")이고,
  활성화 버튼을 따로 눌러야 적용된다.
- 켜고 끄는 단위는 룰 하나. 엔진은 버전 전체를 컴파일하고, 꺼진 룰에 걸린 결과만 판정에서 뺀다.
- 새 버전의 룰은 모두 켜진 상태로 시작한다. 이전 버전에서 꺼 둔 룰과 이름이 같아도 물려받지 않는다.
  필요하면 관리자가 활성화 전에 대기 버전에서 다시 끈다.

### 내가 정하고 사용자가 이의 없다고 한 것

- 버전 번호는 DB 스키마대로 정수다 (`yara_rulesets.rulesets_version`). 서버가 기존 최대값 + 1을 붙인다.
  Notion 명세의 문자열 버전(`2026.09.24`)과 요청 필드 `version`은 쓰지 않는다.
- 업로드는 `.yar` 파일 하나(1MB 이하). 파일 하나에 룰이 여러 개 있어도 된다.
- 컴파일 검증은 탐지 엔진(yara-python)이 한다. api-server는 원문을 엔진에 넘기고 결과만 받는다.
  문법 오류면 엔진의 오류 메시지를 사용자에게 보여주고 거부한다.
- 룰 이름과 심각도는 엔진이 컴파일 결과에서 뽑아 준다. 심각도는 룰의 `meta: severity`
  (LOW/MEDIUM/HIGH/CRITICAL, 대소문자 무시). 없거나 그 밖의 값이면 MEDIUM.
- 룰 원문은 DB에 저장한다 (`yara_rulesets`에 컬럼 추가, 새 Flyway 마이그레이션).
- 활성화는 한 트랜잭션: 기존 활성 해제 → 대상 활성 → `file_verdicts` 중 `verdict_source = 'ENGINE'`인
  행만 `is_stale = true` → 감사 로그. `CheckHash`는 이미 stale 판정을 캐시 미스로 취급하므로
  같은 파일은 다음 다운로드 때 다시 업로드·검사된다.
- 룰 사용 여부는 버전마다 따로다 (`yara_rules.enabled`). 활성 버전의 룰을 바꾸면 바로 반영되고
  엔진 판정을 stale로 만든다. 대기 버전에서 바꾸면 미리 설정만 해 둔다.
- 엔진 반영 방식:
  - api-server가 매 검사 요청(`Analyze` 메타데이터)에 "기대하는 룰셋 상태"를 함께 보낸다.
    상태는 활성 버전 번호와 꺼진 룰 집합을 식별할 수 있는 값이다.
  - 엔진이 들고 있는 상태와 다르면 엔진은 파일을 읽기 전에 검사를 거절한다.
  - 그러면 api-server가 원문과 꺼진 룰 목록을 엔진에 밀어 넣고(새 RPC), 같은 스풀 파일로 한 번 다시 시도한다.
  - 이렇게 하면 엔진이 재시작해 번들 룰로 돌아가도 첫 검사에서 맞춰진다.
  - 엔진에 닿을 수 없으면 기존처럼 fail-close로 차단한다. 별도 우회 경로를 만들지 않는다.
- 엔진은 응답의 `rulesets_version`에 실제로 쓴 버전을 채운다. 지금은 항상 0이다.
  `analyses`와 `file_verdicts`에 올바른 버전이 남는다.
- 지금 엔진에 들어 있는 `eicar.yar`, `teecher_demo.yar`를 합쳐 v1로 미리 넣고 활성 상태로 둔다
  (마이그레이션). 기존 v0 행(룰셋 관리 이전 기록용)은 그대로 두고 목록에서는 숨긴다.
- 업로드 시 엔진에 닿을 수 없으면 업로드를 거부한다 (검증 없이 저장하지 않는다).
- 룰이 0개인 파일은 업로드를 거부한다 (422). 룰을 전부 끄는 것은 허용하되, 활성 버전에서 마지막 켜진 룰을
  끌 때 콘솔 확인 창에서 탐지가 꺼진다고 경고한다.

### 리뷰 뒤 내가 정한 것

- 활성화와 활성 버전의 룰 변경은 DB 커밋 뒤 바로 엔진에 적재를 시도한다(최선 노력). 실패해도 활성화를
  되돌리거나 오류로 응답하지 않는다. 다음 검사 때 "기대 룰셋 상태" 비교로 다시 맞춘다. 업로드 때 같은 엔진으로
  컴파일이 통과한 원문이라 적재 실패는 사실상 엔진이 내려간 경우뿐이고, 그때는 어차피 fail-close로 차단된다.
  503은 업로드에만 쓴다.
- 이미 격리된 파일은 건드리지 않는다. 룰 변경은 앞으로의 다운로드에만 영향을 준다. 격리 파일은 기존 오탐 복원으로 푼다.
- 감사 로그: 활성화는 `ACTIVATE_RULESET`, 룰 사용 변경은 `ENABLE_YARA_RULE` / `DISABLE_YARA_RULE`
  (이미 enum에 있음). 업로드용 액션은 새로 추가한다. 원문은 감사 로그에 넣지 않는다.

## API

모두 Admin REST, 로그인 필요. 응답·오류 형식은 `docs/api-convention.md`를 따른다.

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| GET | `/api/admin/rulesets` | 버전 목록 (최신 버전 먼저). 버전, 룰 수, 꺼진 룰 수, 활성 여부, 올린 시각, 활성화 시각 |
| GET | `/api/admin/rulesets/{version}/rules` | 한 버전의 룰 목록. 룰 id, 이름, 심각도, 사용 여부 |
| POST | `/api/admin/rulesets` | multipart `file` 업로드 → 새 대기 버전 (201) |
| POST | `/api/admin/rulesets/{version}/activate` | 활성화 (200). 이미 활성이면 그대로 200 |
| PATCH | `/api/admin/rulesets/{version}/rules/{ruleId}` | `{ "enabled": true/false }` |

오류: 빈 파일·확장자 다름·크기 초과·형식 오류는 400, 문법 오류는 422(엔진 메시지 포함),
없는 버전·룰은 404, 엔진에 닿지 않으면 503. 422와 503은 `ErrorCode`에 새로 추가한다.

목록 응답의 페이지네이션 방식은 다른 관리 목록과 맞춘다 (`PageResponse`).

## 엔진 (detection-engine)

- 새 RPC 두 개 (`proto/teecher/engine/v1/engine.proto`):
  - 컴파일 검증: 원문을 받아 성공 여부, 오류 메시지, 룰 이름·심각도 목록을 돌려준다. 저장하지 않는다.
  - 룰셋 적재: 버전, 원문, 꺼진 룰 이름 목록을 받아 컴파일하고 메모리의 현재 룰을 바꾼다.
- `AnalyzeMetadata`에 기대 룰셋 상태 필드를 추가한다. 다르면 정해진 gRPC 상태 코드로 거절한다.
- 꺼진 룰에 걸린 매치는 판정과 응답 `matches`에서 뺀다.
- 시작할 때는 지금처럼 번들 `rules/` 디렉터리를 버전 0 상태로 적재한다.
- 컴파일 검증·적재에도 기존 분석과 같은 수준의 크기 제한을 둔다.

## 콘솔

- 메뉴 "YARA 룰셋"(`/rulesets`, 지금은 빈 화면)을 채운다.
- 왼쪽 버전 목록: 버전, 상태(적용 중 / 대기 / 이전), 룰 수, 올린 시각. 기본 선택은 적용 중 버전.
- 오른쪽: 선택한 버전의 룰 표(이름, 심각도, 사용 토글)와 "이 버전 활성화" 버튼.
  적용 중 버전이면 버튼 대신 "적용 중" 표시.
- 상단 ".yar 업로드" 버튼. 업로드에 성공하면 새 버전을 선택해 보여준다.
  문법 오류면 엔진 메시지를 그대로 보여준다.
- 활성화와 적용 중 버전의 룰 끄기는 재검사를 일으키므로 확인을 한 번 받는다.
- mock 모드용 MSW 핸들러와 데이터를 함께 만든다 (다른 화면과 같은 방식).

## 빌더에게 맡기는 것

- 엔진 RPC·필드 이름, 거절할 때 쓰는 gRPC 상태 코드, "기대 룰셋 상태" 값의 구체적 형태
- 마이그레이션 번호와 컬럼 이름
- 콘솔 컴포넌트 구조, 토글·확인 창 모양 (화이트리스트 화면 스타일 안에서)
- 테스트 구성 (서버 단위·통합, 엔진 pytest, 콘솔 vitest — 각 모듈의 기존 방식을 따른다)
