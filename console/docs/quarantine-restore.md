# 격리 파일 오탐 복원

## 범위

- 브랜치 `feat/console-quarantine-restore`, 시작 기준 develop `76e635a`.
- 게시 전 최신 develop `be0793b`로 fast-forward하고 보존한 복원 변경을 다시 적용했다. 충돌은 없었고 복원 기능 소스 8개는 기존 리뷰본과 동일하다. 백업 stash는 삭제하지 않았다.
- 기존 격리 상세에 오탐 복원 버튼, 확인 화면, 선택 사유, 성공 후 상세 재조회를 추가한다. 백엔드 코드는 수정하지 않는다.
- 복원은 격리 상태를 RESTORED로 바꾸고 SHA-256을 화이트리스트에 등록/재활성화한다. 같은 해시의 활성 블랙리스트는 서버 리스너가 해제한다. **PC로 파일을 전송하거나 다운로드하는 기능이 아니다.**
- QUARANTINED 상태만 복원한다. RESTORED/DELETED/EXPIRED에는 복원 버튼을 표시하지 않는다.

## 코드 흐름

- `lib/api/quarantine.ts`의 기존 `restoreQuarantineFile()`에 선택 사유를 추가했다. 사유 앞뒤 공백은 제거하고 비어 있으면 본문을 생략해 서버 기본값 `오탐 복원`을 사용한다.
- `QuarantineDetailPage.tsx`는 URL별로 별도 화면 인스턴스를 사용한다. GET cleanup, 요청 회차, 마운트 여부를 검사해 이전 파일의 응답이나 확인 입력을 새 파일에 표시하지 않는다.
- ref 잠금과 비활성 버튼을 함께 사용해 연속 클릭도 POST 한 건만 전송한다. 복원 중 재조회나 사유 변경도 막는다.
- `QuarantineRestorePanel.tsx`는 대상 파일명과 전체 해시, 화이트리스트/블랙리스트 영향을 먼저 안내한다. 확인 화면을 열 때 설명 영역으로 포커스를 옮기며 위험한 확인 버튼에는 자동 포커스하지 않는다.
- POST 성공은 즉시 상세에 반영하고 GET으로 재확인한다. 후속 GET만 실패하면 복원 성공을 취소하지 않고 이전 상세와 조회 오류/재시도를 함께 표시한다.
- 실패 시 사유를 보존한다. `quarantineRestore.ts`에서 400/401/403/404/409와 결과를 알 수 없는 통신 오류를 구분한다.
- POST 응답만 끊겼을 수 있으므로 실패 뒤에는 상태 재조회를 먼저 요구한다. 확인창을 취소하고 다시 열어도 이 제한은 유지한다. GET 성공 후 QUARANTINED가 확인되면 다시 복원할 수 있다. 자동 POST 재시도는 하지 않는다.
- 완료 안내는 복원 패널 안에서 3초간 표시하고 오류는 자동으로 숨기지 않는다.
- mock 복원은 선택 사유/기본값, QUARANTINED 한정, 비활성/만료 화이트리스트의 최초 등록 시각 보존, 유효 화이트리스트 보존, 같은 해시의 차단 해제, 관련 감사 로그를 실제 계약에 맞춘다. 목록과 상세 mock은 변경하지 않는다.

## 검증

- 시작 기준 lint/build/85개 통과. 구현 후 lint 경고 없이 통과, production build와 전체 프론트 109개 통과.
- 최신 develop 통합 뒤 npm ci, lint, production build, 전체 프론트 180개를 다시 통과했다. 기존 서버 복원 통합 테스트도 다시 실행했다. 기존 PC/바이패스/대시보드 변경은 develop에서 받은 내용이며 복원 PR의 신규 구현으로 계산하지 않는다.
- 기존 서버 `QuarantineRestoreRestIntegrationTest` 9개 통과. 새 Java 테스트나 백엔드 변경은 없다.
- React DOM 테스트로 선택 사유, 확인 취소, 상태별 버튼, 연속 클릭 1건, 오류 후 입력 보존, 취소/재진입의 중복 방지, POST 성공 후 GET 실패, 화면 이동 뒤 늦은 GET/POST 무시를 검증했다.
- 실제 API와 격리된 QA DB에서 복원 전후 상태/복원 시각, 유효 화이트리스트 1행, 사유, RESTORED 출처와 격리 ID를 다시 조회했다.
- 실제 요청 응답 전달을 보류해 연속 클릭 시 POST 1건/컨트롤 잠금을 확인했다. 의도적으로 POST를 차단한 경우 사유 보존과 재조회 후 복원을 확인했다.
- 실제 POST가 서버에 반영된 뒤 응답만 유실시킨 경우, 재전송 없이 GET으로 RESTORED를 확인했다. 사유 생략 시 DB/API의 기본 사유도 `오탐 복원`이었다.
- 별도 요청으로 먼저 복원한 대상은 실제 409, 화면 로드 뒤 QA 샘플 한 건만 삭제한 대상은 실제 404를 확인했다. 각각 입력 보존과 상태 재조회 흐름을 확인했다.
- RESTORED/DELETED/EXPIRED의 복원 불가 표시, 390/1024/1440px에서 페이지 가로 넘침 없음과 확인 패널 포커스를 확인했다.
- 루트, 블랙리스트, 인증, 학습 주석, PC 목록 worktree의 기존 작업 상태와 변경 파일 SHA-256을 작업 전후 비교해 보존을 확인했다.

## 테스트 데이터와 한계

- API `http://100.70.241.6:18084`, 기존 격리 QA 프로젝트 `teamc-console-remaining-qa`를 사용했다. C1의 PC 36개는 수정하지 않았다.
- C2 전용 무해한 문자열의 SHA-256/바이트 길이로 격리/이벤트/판정 메타데이터 9세트를 추가했다. 실제 파일 다운로드, 엔진 판정, S3 객체가 생성된 결과가 아니다.
- 정상/기본 사유/통신 실패/충돌 샘플 4개는 실제 복원했다. 조회 후 사라지는 404 검증에 사용한 샘플 한 건만 삭제했다. 초기 검증 종료 시점의 샘플은 RESTORED 5개, QUARANTINED/DELETED/EXPIRED 각각 1개, 총 8개였다. 이후 사용자 수동 복원과 촬영용 샘플 추가로 상태와 개수가 달라질 수 있다. 초기 RESTORED 한 건은 표시 검증용 직접 입력 메타데이터이며 실제 복원 결과와 구분한다.
- 브라우저 검증은 로컬 인증을 끈 환경이다. 프론트 로그인/권한 통합은 C4에서 별도로 확인한다. 업무 계약 테스트의 인증 stub도 인증 검증으로 간주하지 않는다.
- npm audit의 source-map-js/vite high 2건은 작업 시작부터 존재했다. 별도 범위의 의존성을 임의로 갱신하지 않았다.
- DOM 상호작용 테스트를 위해 jsdom 30.1.3을 개발 의존성으로 추가했다. Node 요구 범위는 `^22.22.2 || ^24.15.0 || >=26.0.0`이며 검증 환경은 Node v26.9.0이다.

## 직접 확인

- 독립 리뷰에서 보안/로직 차단 이슈는 없었다. 실제 UI/API 검증과 자동 테스트 결과를 함께 확인했다.
- 비차단 테스트 보완 제안: 유효 화이트리스트/같은 해시 차단 해제/감사 로그의 mock 검증 확대, 결과 불명 후 상태 GET도 실패하는 경우의 잠금 유지, 화면 이동 후 이전 POST 실패 응답 무시를 각각 추가 회귀 테스트로 명시할 수 있다. 현재 구현의 오류로 판정된 항목은 아니다.

- 실제 복원 완료 샘플: http://100.70.241.6:5181/quarantine/9e69aa63-c67b-4709-b741-ce616d8e1a60
