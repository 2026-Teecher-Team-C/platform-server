# 블랙리스트 관리

## 코드 흐름

- `BlacklistPage.tsx`는 검색 조건, 마지막 조회 결과, 선택한 항목과 쓰기 요청 상태를 관리한다. 조회에는 기존 domain client와 mock/real 전환을 사용하며 `PageResponse`의 page는 0부터 시작한다.
- 검색은 해시 앞부분(1~64자리 16진수), 심각도, 출처, 활성 여부다. 활성 여부 생략은 활성만, false는 비활성만이므로 전체 선택지는 없다.
- `BlacklistCreateForm.tsx`는 64자리 SHA-256과 비어 있지 않은 사유를 확인하고, 실패하면 입력을 유지한다. 심각도와 출처는 입력받지 않으며 서버가 HIGH/MANUAL로 결정한다.
- `runChange()`는 등록, 사유 수정, 해제 요청을 공통 처리한다. ref 잠금으로 렌더링 전의 연속 클릭까지 막고, 서버 성공 후에만 성공 안내와 목록 재조회를 수행한다.
- 등록 후에는 검색 조건을 비우고 활성 목록 첫 페이지로 이동하며 페이지 크기는 유지한다. 신규 등록은 최신순으로 표시하지만 재등록의 최초 등록 시각은 서버 정책대로 유지한다. 직접 전체 해시로 검색한 항목은 해제 후 해당 해시 조건만 비운다. 성공 안내는 3초 뒤 사라지고 오류 안내는 유지한다.
- `ClearableHashInput.tsx`는 등록/검색 해시 칸의 지우기 버튼을 공통 처리한다. 버튼은 폼을 제출하지 않고 해당 해시만 비우며 입력 칸으로 포커스를 돌려준다. 요청 처리 중이거나 입력이 비어 있으면 비활성화한다.
- `BlacklistNotice.tsx`는 성공 메시지를 화면 오른쪽 아래 고정 토스트로 표시해 표와 검색 폼을 밀지 않는다. 3초 뒤 자동으로 사라지며 닫기 버튼으로 바로 닫을 수 있다. 오류 안내는 기존 입력/확인 패널에 유지한다.
- `BlacklistActionPanel.tsx`에서 사유 수정, 활성화, 비활성화를 확인한다. 활성 항목은 사유 수정/비활성화, 비활성 항목은 활성화 버튼을 제공한다. 비활성화는 화이트리스트 등록이나 다운로드 자동 허용을 뜻하지 않는다.
- 비활성화는 기존 DELETE, 활성화는 기존 POST 등록 API를 사용한다. 활성화 사유는 기존 값으로 채우며 수정할 수 있다. 활성화 시 심각도 HIGH/출처 MANUAL 변경과 최초 등록 시각 유지를 확인 화면에서 안내한다. 실패하면 확인 패널과 사유를 보존하며 쓰기 잠금으로 중복 요청을 막는다.
- 상태 변경 후에는 현재 활성 여부와 일반 검색 조건을 유지한다. 변경한 항목이 현재 목록에서 빠지는 경우 전체 해시 검색만 비우고, 마지막 페이지가 없어지면 페이지를 보정한다. 신규 등록의 첫 페이지 이동과는 구분한다.
- 기본 정렬은 서버의 created_at DESC, hash_value DESC다. 재활성화 시 최초 등록 시각을 유지하므로 목록 맨 위로 이동시키지 않는다.
- 표 아래쪽에서 해제를 눌러도 경고가 보이도록 확인 패널로 포커스를 옮긴다. 파괴적인 확인 버튼 자체에는 자동 포커스하지 않는다.
- 재조회 중에는 기존 표와 페이지 정보를 유지하며 200ms 이후 진행 상태를 표시한다. 마지막 페이지의 마지막 항목이 없어지면 존재하는 마지막 페이지로 다시 조회한다. 오래된 요청의 응답은 무시한다.
- `lib/blacklist.ts`는 입력 검증과 400/401/403/404/409 오류 안내를 담당한다. 네트워크 실패는 서버 반영 여부가 불분명할 수 있으므로 먼저 목록을 확인하도록 안내한다.
- mock도 재활성화 시 최초 등록 시각 보존, 유효한 화이트리스트 충돌과 만료된 화이트리스트 허용, 204 해제, 감사 로그 기록을 서버 계약에 맞춘다. 사유 수정의 감사 로그 상세에는 서버와 동일하게 previousReason, newReason을 남긴다.

## 검증 범위

- 상태별 버튼, 비활성화 → 비활성 목록의 활성화 버튼 → 활성화 → 활성 목록의 비활성화 버튼을 실제 API로 검증했다. 빈 활성화 사유는 요청 0건, 네트워크 실패 후 사유 보존, 재시도 중 연속 클릭은 실제 POST 1건임을 확인했다. API 재조회로 isActive/사유/HIGH/MANUAL/해제 시각 초기화/최초 등록 시각 보존을 확인했고 390px에서 페이지 넘침이 없었다.

- 최신 develop `61c9425` 기준. 콘솔 lint, production build, 자동 테스트 74개 통과. 팀원의 화이트리스트와 감사 로그 구현을 보존했으며 백엔드 소스는 수정하지 않았다.
- 기존 서버의 목록, 등록, 사유 수정, 해제 통합 테스트 4종, 총 37개 통과.
- 실제 API와 별도 테스트 DB로 등록 → 사유 수정 → 해제 → 비활성 조회 → 재등록, 감사 로그 기록을 확인했다.
- 성공 토스트의 고정 위치, 수동 닫기, 3초 자동 닫기, 390px 화면 내 표시를 브라우저로 확인했다. 실제 API를 다시 조회해 해제 후 isActive=false/해제 시각, 같은 해시 재등록 후 isActive=true를 확인했다.
- 잘못된 해시/빈 사유, 중복/화이트리스트 충돌, 만료된 화이트리스트 허용, 요청 차단 후 입력 유지와 재시도, 다른 관리자가 해제한 항목의 404, 등록/해제 연속 클릭 시 단일 요청을 확인했다.
- 해시 앞부분이 같은 샘플 21개로 마지막 페이지의 마지막 항목 해제 후 페이지 보정을 확인했다. 경계 검증용 21개만 정리했고 일반 확인용 샘플은 남겼다.
- 실제 GET 응답의 전달을 보류한 동안 새 해시를 등록한 뒤 이전 응답을 늦게 전달해도 새 검색 결과가 덮어써지지 않는지 확인했다. 중복 클릭, 페이지 보정, 늦은 응답 검증은 브라우저 실행으로 확인했으며 정적 렌더링 단위 테스트와 구분한다.
- 390/1024/1440px에서 페이지 전체의 가로 넘침이 없고, 하단 행에서 연 확인 패널이 화면 안에 보이는지 확인했다.
- 화면 검증 환경은 로컬 인증을 끈 별도 서버다. 로그인 기능이나 실제 다운로드/엔진 검사 검증과는 구분한다. 테스트 해시는 무해한 문자열에서 계산했으며 실제 악성 판정 결과가 아니다.
